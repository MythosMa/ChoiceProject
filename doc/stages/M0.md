## 1. 目标

**在动任何玩法之前，先让"每一批都能被复核"。**

一句话：*没有断言、没有独立试玩场景、没有截图，"验收"就只能靠你反复试玩——那是不可持续的方式。*

## 2. 效果（做完之后会有什么不同）

1. **一条命令跑完机制断言**，全绿/全红一目了然，不需要你打 100 遍来验证一条规则；
2. **F5 直接进试玩场景**（`arena_01`），不再进调试用的测试场景；
3. **我能给你改前/改后的截图对比**，而不是让你自己开来看；
4. 从这一阶段起，每个阶段都能**独立回滚 + 回归**（`stage/mN` 分支 + tag）。

> 这一阶段**不改变任何手感、数值、玩法**。你的三分钟验收只要一句"没退化"。

## 6. 风险与回滚

| 风险 | 处理 |
|------|------|
| headless + C# 的运行时行为与带窗口时不同（例如相机为 null） | 现有代码已判空；断言只依赖节点/数值，不依赖渲染 |

**A3 基线数据（冻结 AI / 玩家无敌，纯输出）：**

| 脚本 | 结果 |
|------|------|
| 交替 jab + heavy | 击杀 50 HP 敌人 = **158 帧（2.63 秒）** → 0.316 HP/帧 |
| 同名 jab 连打 | 240 帧后敌人**剩余 32/50**（第 3 下被识破后，输出被霸体锁死） |

> 换算：M1 的 240 HP ≈ 758 帧纯输出（12.6 秒）；按约 50% 实际输出时间估算 ≈ 25 秒 —— **`COMBAT_SPEC` 定的 240 HP / 20–25 秒是合理的**。

### 偏差 / 意外

1. **测试会让玩家死亡**：A3 最初的"同名 jab 连打"脚本被霸体反击打死 → `Player` 触发 `ReloadCurrentScene` → 测试场景重载 → **测试无限重跑**（首次运行 60 秒超时）。
   已修：所有战斗类用例先置 `player.invincible = true`；并在 `TestRunner` 头部写死这条约定。
2. **同名 jab 打不死敌人**（第 3 下被识破后输出锁死）——这正是 M1 要修的免费解的**反面**。基线改用"交替 jab/heavy"。
3. 截图不能 headless 做（无渲染）：走 `godot_run_project` + `eval` 保存 viewport。已完成并留档 `doc/images/2026-11-04-arena.png`。
4. godot-bridge 插件会往 `project.godot` 注入 `McpInteractionServer` autoload，已从仓库排除（`.gitignore` + 提交前还原）。

### 第四轮追加（2026-11-04，1A-8）

**问题（用户实测）：** 被识破架住（-18）之后，敌人又"扑空踉跄"，玩家反过来白拿 ×3 —— **因果倒挂**。

**根因：** 架住只结算伤害，没有结束敌人的这一刀。敌人仍从 Startup 走到 Active，
玩家在硬直中躲开/拉开 → `hasConnected = false` → 命中"预判非空且未命中"的 Stagger 分支。

**修复：** `EnemyStateMachine.OnArmorPunishResolved()` —— 架住即回合结算：
清预判、关判定框；前摇/判定中直接回 Idle（玩家仍在硬直，回合归敌人）；后摇中只清预判、保留后摇。

**新增断言 A6：** 架住后手动推进敌人相位机 90 帧，不得出现 Stagger，敌人不得再掉血。

### 第七轮追加（2026-11-04，1A-11）

| # | 改动 | 实现 |
|---|------|------|
| 1 | **出招位移数据化** | `MoveData` 增加 `startupShift / activeShift / recoveryShift`（相对朝向，像素，按段帧数均摊成速度）；`CombatHandler.ApplySegmentShift()` 写 `Player.combatVelocityX`，由 Player 统一积分 |
| 2 | 重拳配位移 | 起手 -4 / 判定 +12 / 后摇 -8，净位移 0；轻拳三段全 0 |
| 3 | 实测 | 重拳 x: 600 → 596.3（后拉）→ 608.3（前冲）→ 600.3（回位）；轻拳 x 全程不变 |

> **设计说明：** 判定框是身体的子节点，会跟着位移一起动——**判定期前冲 = 动态延长攻击距离**。
> 后续突进 / 升龙 / 后撤斩直接复用这组字段，不需要改代码。

> **事故记录（uid 缓存）**：重命名 `.tres` 后，`.godot/uid_cache.bin` 仍指向旧路径，导致场景按 uid 解析失败；
> 清掉缓存后，**autoload 的 `*uid://...` 引用**因为缓存缺失而解析成 `.`，`InputManager.Instance` 变 null，
> 引发 `TryDodgeInterrupt` 的 NRE 连锁（测试 2/4 失败）。
> **修复：** 把 `[autoload]` 改成 `*res://core/InputManager.cs` 这样的**路径引用**（不依赖 uid 缓存），
> 缓存由引擎在下次加载时自动重建。教训：**autoload 不要用 uid**。

## 8. 阶段回顾（完成后填写）

**交付了什么**

| 类别 | 内容 |
|------|------|
| 工程 | `tests/` headless 断言框架（7 条）；`arena/` 与 `test_scenes/` 分离；截图流程；分支 + tag 制度 |
| 操作 | 轻/重改由按键决定（Z/X）；脚键暂时失效；闪避穿过敌人；三段出招位移（数据驱动） |
| 规则 | 识破的"被预判的一击"不再造成伤害；架住即回合结算；**回合归属立为全局铁律** |
| 数据 | 招式身份 `moveId` + `displayName`；表现参数 `accentColor/sparkAmount`；位移 `*Shift` |
| 表现 | 轻拳细长冷蓝 / 重拳粗大橙色；实体挥击块；命中火花分级；敌人血条；HUD 中文字体修复 |

**三个值得记住的坑**

1. **回合归属**：一次交互必须结算清楚"谁赢"——两次事故（双叠惩罚、架住后白拿踉跄）都源于此。已立为铁律。
2. **uid 缓存**：autoload 用 `*uid://` 引用，缓存一旦失效就解析成 `.`，引发连锁 NRE。已改路径引用。
3. **中文字体**：系统回退解析成 PingFang **HK**（繁体），"敌"缺字变方块。已显式指定简体字库。

**一条流程经验**：阶段一旦允许"顺手加"，范围会很自然地膨胀（M0 从 1 个批次变成 11 个）。
这次没出问题，是因为每加一项都记进了阶段文档，并保持了"断言 + 截图 + 三分钟"的验收节奏。
**但 M1 要收紧了**——M1 的核心只有一件事：给敌人回合。
