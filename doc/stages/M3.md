# 阶段 M3 · 外部验证

> 分支：`stage/m3`  |  开始：2026-11-05  |  状态：🔨 进行中
> 上游：[ROADMAP](../ROADMAP.md) §三 M3　|　前置：[M2](M2.md) 已验收

---

## 1. 目标

**把"玩家会自己发明漏洞"这件事提前到有人陪你一起发现。**

M0 和 M2 都出现了同一个模式：机制第一天写完，剩下全部时间在修"玩家找到的新免费解"。
这些漏洞**只有真人能发明**——而目前唯一的真人是作者本人，他已经打到腻了。

M3 要问的只有两件事：

1. **没见过这个项目的人，会不会自发地换招 / 收手？**
2. **他失败之后，能不能说出"我该换一招"？**

> **不过 = 停止加内容。** 这是全项目最重要的一道闸门。

## 2. 效果（做完之后会有什么不同）

1. 我们第一次知道：这套"读招"在**没有设计师解释**的情况下，陌生人能不能自己看出来；
2. 如果看不出来，问题大概率在**提示（tell）**，不在机制；
3. 如果看得出来但**不想换招**，问题在**收益结构**。

## 4. 验收标准

### 测试方法

- 找 **3 个**没看过本项目的人（可以是朋友/同事，**不要是你自己**）；
- 每人 **10 分钟**，只告诉他键位，**不解释读招/格挡/闪避机制**；
- 你在旁边**只看不说**，记录行为，不提示。

### 观察点（逐条记录）

| # | 观察 | 记录什么 |
|---|------|---------|
| 1 | 他会不会**换招** | 前 60 秒内有没有主动切换 jab / 重拳 |
| 2 | 他会不会**收手** | 有没有出现"打两下就停"的停顿 |
| 3 | 他会不会**用格挡** | 有没有按下格挡并因此减少伤害 |
| 4 | 他会不会**躲反击** | 有没有躲开识破反击 |
| 5 | 失败后能不能**说出原因** | 问他："刚才为什么被打死了？" |

### 通过线

- **观察点 1 或 2**：3 人里**至少 2 人**出现；
- **观察点 5**：3 人里**至少 2 人**能说出"我该换招 / 该停手"这类原因；
- 且没有"这游戏看不懂/不知道在干什么"的评价。

**不通过 → 停止加内容，回去修 tell 与收益结构；通过 → 进入 M4（第二敌人）。**

## 6. 风险与回滚

| 风险 | 处理 |
|------|------|
| 找不到 3 个人 | 2 人也算有效（但结论标注样本小） |
| 测试者提前问了机制 | 告诉他"你先玩，玩完我再解释" |
| 导出构建跑不起来 | 只跑 Mac 本机也算（写明局限） |
| 测试者觉得太简单 | 这正是要记录的信息——不是失败，是"简单到不需要判断" |
