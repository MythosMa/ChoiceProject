# 阶段文档（Stage Docs）

> **规矩（2026-11-04 起）：** 每个阶段开工前，先写一份本文档，再建分支，再动代码。
> 写完不验收不许合并；验收不过不许进下一阶段。

## 1. 流程

```
写阶段文档 → 建分支 stage/mN → 分批实现（每批一个 commit）
   → L1 断言全绿 → L2 人打三分钟 → 合并 main（--no-ff）+ tag mN-accepted
   → 不通过：分支留作复盘，main 不动，回到设计讨论
```

## 2. 分支策略

| 分支 | 含义 |
|------|------|
| `main` | **只放已验收的东西**（文档 + 通过的阶段） |
| `stage/mN` | 第 N 阶段开发分支，从 main 切出，只做本阶段范围 |
| tag `mN-accepted` | 该阶段通过验收的时间点 |

**为什么值得这么做：** 每个阶段都是一个可回滚、可回归的完整状态。
出问题时 `git checkout stage/m3` 就能把整盘回到那个阶段，`dotnet build` + 断言跑一遍就知道有没有退化。

**合并方式：** `git merge --no-ff stage/mN`（保留阶段边界，方便日后 `git log --first-parent` 看主线）。

## 3. 文档模板

```markdown
# 阶段 MN · <名字>

> 分支：`stage/mN`  |  开始：YYYY-MM-DD  |  状态：🔨/✅/❌
> 上游：ROADMAP §三  |  规格：COMBAT_SPEC §八

## 1. 目标（一句话）
## 2. 效果（做完之后，玩起来/用起来有什么不同）
## 3. 范围（In / Out，Out 要写明为什么）
## 4. 验收标准
   L1 机制断言（可自动跑）
   L2 手感（人打三分钟，观察点写死）
   L3 外部（仅 M3 需要）
## 5. 批次拆分
## 6. 风险与回滚
## 7. 完成记录（验收后补：日期 / 结论 / 偏差）
```
